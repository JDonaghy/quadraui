- Every editable text widget undoes and redoes through one shared history
  (#2978 TE7): `behaviour::text_edit::EditHistory` serves `EditOp::Undo`/
  `EditOp::Redo` for `TextEditor`, `LinesEditState` (`TextInput`) and
  `FlatEditState` (`TextField`, `CommandLine`, the palette query,
  `PasswordInput`, `TextArea`, ...). Ctrl/Cmd+Z undoes and Ctrl/Cmd+Shift+Z
  redoes in every one of them; with nothing to give back the chord stays
  `Ignored`, so an app accelerator still fires. The history survives a
  focus change. **Breaking:** `FlatEditState` and `LinesEditState` gain a
  `history` field and are no longer `Copy`, and neither are
  `DualModePaletteState` and `PathPickerEditState`, which hold one.
- **Breaking:** `form::TextCursor` gains a `history: EditHistory` field so
  a `Form` text row keeps its undo history while it holds focus; code that
  builds a `TextCursor` literal adds `history: EditHistory::default()`.
- `TextInput` paints the caret its own `TextInputState` walked to, not the
  descriptor's `cursor_line`/`cursor_col` (#2978 TE11), so a host that
  never echoes a caret back still sees it where typing lands.
  `TextInputPrimitiveLayout` gains `line_height`, `units` and `relayout`.
- `"text_input"` (`TextInput`) and `"text_field"` (`TextField`) join the
  static `widget_kinds!` table.
- `quadraui-binding-core`: `"text_input"`, `"text_field"`, `"password"` and
  `"textarea"` are generic `LeafDescriptor::Widget` leaves decoded through
  `widget_kinds!` and edited through the core widgets' own `Interactive`
  state; their `ExtraPaint` impls, the binding-side `PasswordInput`/
  `TextArea` wrappers, `extra_as_text_input` and `text_input.rs`
  (`TextEditorCache`, `text_input_key_event`, `text_input_insert_event`,
  `text_input_click_event`, `apply_text_input_edit`, `clamp_cursor`) are
  deleted, along with `InteractionEngine::sync_text_input_carets`.
  `InteractionEngine::paint_with_widget_state(paint)` installs the
  engine's per-widget state for a paint pass, so every generic leaf paints
  from the state its own input handling walked; that state is keyed by the
  widget's own id (else the leaf id). A dialog's or popover's layout
  subtree routes keys and committed text to a focused generic leaf
  through the same dispatch.
- The `"menu_bar"` wire kind decodes to `AppMenu`, the whole application
  menu with its dropdown cascade as popups, instead of the bare `MenuBar`
  strip (#2977, 0.12 rec 12). `AppMenu` and `MenuDef` derive `JsonSchema`
  under the `schema` feature. An `AppMenu` whose `view` is the default is
  uncontrolled: it keeps the view it moves to in the new
  `AppMenuState::view` and paints, opens its popups and handles input
  from it, so a host that never applies `AppMenuEvent::Changed` still has
  a working menu. A host that applies it controls the view as before.
- Binding-core delivers a key a focused generic leaf answers `Ignored`
  after emitting its own report of it (a tab bar's scoped `KeyPressed`)
  once, as that report, and not also as the raw `KeyPressed`.
- `Form`'s widget contract reads its live state (#2977): its layout and
  paint apply the stored `FormState`'s scroll offset, caret and field
  focus, so a wheel notch or a scroll-into-view moves what is painted and
  hit-tested; a host reporting the form focused through
  `PaintState::focus_ring_visible` shows its focused-row highlight. Its
  `Interactive::handle` requests focus for the newly focused field's stop
  (`FocusSpec::Children`'s sub-target) whenever field focus moves, so a
  host knows which child holds focus; moves field focus on a plain Up/Down
  the focused field has no use for, stopping at either end; and captures
  the pointer for a slider drag. `FormDialog`'s Tab hand-off reads the
  form's live field focus, so it follows focus the form tracks itself.
- `TabBar`'s keyboard navigation starts from the descriptor's
  `chrome.focused_index` while its `TabBarState` names no tab (#2977), so
  a host that threads keyboard focus through the descriptor keeps its
  place: Right moves on from that tab and Enter activates it.
- `ListView`, `TreeView`, `DataTable`, `TextDisplay`, `TabBar` and
  `CellGrid` keep their scroll, selection, active tab, expansion and
  navigated scroll in their own `Interactive::State` and resolve it
  uncontrolled by default (#2977): the descriptor's value wins only when it
  changed since the widget last moved, so an app that never echoes a move
  still sees it, and one that does sees its own value. `TreeView`
  collapses a branch it toggled itself by dropping its descendants. Each
  move still emits the widget's existing event. `ListView` handles the
  wheel and its own scrollbar (thumb drag and track paging), reporting
  `ScrollOffsetChanged`. A windowed `ListView`/`DataTable` answers
  Ctrl+A and Shift/Ctrl extension as a plain cursor move, since a selection
  over the whole total would be unbounded.
- **Breaking:** `ListView` and `TreeView` no longer implement `Eq` (their new
  `scroll_px: Option<f32>`), and `TextDisplayState`/`CellGridState` no
  longer implement `Copy` (#2977). Every struct literal of the four row
  widgets needs `items_window` (and `scroll_px` where it exists): add
  `items_window: None` (and `scroll_px: None`) to each.
- A layout-tree `text_display` leaf's selectable text region is now
  registered under the descriptor's own `id` rather than the leaf's
  tree-address id (#2977), so `TextSelectionChanged`/`TextCopied` name the
  display the way they already did for a top-level `text_display`.
- `quadraui-binding-core` drives every widget leaf through the generic
  widget path (#2977): `list`, `tree`, `data_table`, `text_display` and
  `tab_bar` decode to `LeafDescriptor::Widget` (now the only variant) and
  paint, hit-test and route through their core widget, keeping selection,
  scroll, expansion and the active tab in its own state and asking for
  rows through `Interactive::data_requested`. `RenderFrame` and
  `BindingHost` carry one `widgets` map; `draw_bands(backend, widgets,
  hits)` paints it in `WIDGET_KINDS` order (the five kinds first, four
  lines tall for `list`/`tree`/`data_table`, three otherwise).
  `resolve_layout_node(engine, backend, area, node)` resolves container
  state only (split ratio, scroll offset, a tab group's pane, which follows
  its strip's own `TabBarState`) and keeps the widget state of a subtree a
  container hides through `InteractionEngine::keep_widget_states_alive`.
  `widget_state_snapshot(engine, id)` reads a painted widget's
  `StateSummary` (by its leaf or descriptor id) plus a split ratio, and
  `WidgetStateSnapshot` is `{ summary (flattened), ratio }` with the same
  wire shape. `InteractionEngine::activate_tab` activates a painted tab
  bar's tab. A `TabActivated`/`TabClosed`/`RowToggleExpand` the app
  dispatches reaches the painted widget it names through the new
  `Interactive::follow_event` hook, so its uncontrolled state follows, and
  a quadraui-ffi slot decodes through `quadraui::decode_widget` into the
  host's widget map behind the unchanged C ABI. See the bindings'
  changelogs for the py/node-visible event changes.
- `Interactive::follow_event` and `Interactive::settle` (#2977), defaulted
  hooks mirrored on `DynWidget`: an event the host delivered on the app's
  behalf that names the widget (`TabBar` and `TreeView` follow theirs), and
  what a layout resolved recorded into state before paint —
  `DrawsPrimitives::draw_dyn` calls `settle` after laying a widget out and
  lays it out again when it changed state. `TreeView` uses it to scroll a
  selection the app moved into view.
- `ListView`, `TreeView`, `DataTable` and `TabBar` implement
  `Primitive::measure` (row count times the line height; a tab bar's label
  widths, three rows tall), and `TextDisplay::measure` no longer clamps to
  `avail.height` (#2977), so a container sizes them to their content.
- `ListView` and `DataTable` follow a selection the app moves (#2977):
  a new descriptor `selected_idx` outside the viewport scrolls into view
  through `Interactive::settle`, as `TreeView`'s `selected_path` already
  did, unless the app also sets `scroll_offset` that frame (or pins a
  non-zero one from the first frame). The rule is the shared
  `HostLatch::<usize>::follow_selection`, which `TreeView` now uses too, so
  a tree's pinned `scroll_offset` also stands over its app-moved selection.
